# Claude 실전 워크플로우 — 내 작업에 맞춘 운용 매뉴얼

> [!abstract] 이 노트의 목적
> 이론 가이드([[프롬프트 엔지니어링 완전 정복 가이드]], [[Claude 마스터 가이드]])를 **실제 일상 작업에 적용하는 워크플로우**. Claude Code 터미널 환경에서, 문서 작성 · 리서치 · 자동화 에이전트 구축 작업을 최적화하기 위한 운용 매뉴얼이다.

---

## Phase 0: 환경 세팅 — 한 번만 하면 되는 것들

### 0-1. CLAUDE.md 계층 설계

모든 것의 기반. **반복하는 지시를 코드화**하는 것이 첫 번째 단계다.

**글로벌 설정** (`~/.claude/CLAUDE.md`):
```markdown
# 글로벌 규칙

## 언어
- 한국어로 대화한다
- 코드 주석은 한국어
- 커밋 메시지는 영어

## 응답 스타일
- 불필요한 서두/맺음말 생략
- 추측은 "추측:" 라벨 붙이기
- 확실하지 않으면 "확인 필요"라고 명시
- 과도한 엔지니어링 금지: 요청된 것만 변경

## 컨텍스트 관리
- 컨텍스트 윈도우가 자동으로 압축됩니다
- 토큰 예산 걱정으로 작업을 일찍 중단하지 마세요
- 한계에 가까워지면 진행 상황을 메모리에 저장하세요

## 작업 습관
- 큰 작업은 먼저 계획을 세우고 확인 받은 뒤 실행
- 파일 수정 전 git commit으로 체크포인트 생성
- 테스트는 제거하거나 편집하지 말 것
```

**프로젝트별 설정** (`./CLAUDE.md`):
```markdown
# 프로젝트: [프로젝트명]

## 기술 스택
- [사용 중인 기술 나열]

## 코드 컨벤션
- [이 프로젝트 특유의 규칙]

## 구조
- [디렉토리 구조 간략 설명]

## 주의사항
- [이 프로젝트에서 특히 조심할 것]
```

> [!tip] 핵심 원칙
> CLAUDE.md에는 **안정적이고 반복되는 정보만** 넣는다. 변동성 있는 정보(현재 작업 상태 등)는 `progress.txt`나 스킬로 분리한다. 해커톤 우승자도 CLAUDE.md를 "팀 전체가 공유하는 살아있는 지식 베이스"로 다루었다.

### 0-2. 핵심 서브에이전트 3종 세팅

작업 유형별로 **역할을 분리**한다. 이것이 해커톤 우승자가 강조한 "누가 할지의 분리"다.

**`.claude/agents/researcher.md`** — 리서치 전담:
```yaml
---
name: researcher
description: 주제를 깊이 조사하고 구조화된 보고서를 작성
tools: Read, Glob, Grep, WebFetch, WebSearch
model: sonnet
---
당신은 리서치 전문가입니다.

## 작업 방식
1. 먼저 조사 범위와 핵심 질문을 정의
2. 다양한 소스에서 정보 수집
3. 상충되는 정보가 있으면 출처와 함께 병기
4. 결론은 "확실한 것 / 가능성 높은 것 / 추가 확인 필요"로 구분

## 출력 형식
- 핵심 발견 요약 (5줄 이내)
- 상세 분석
- 출처 목록
- 추가 조사가 필요한 영역
```

**`.claude/agents/writer.md`** — 문서 작성 전담:
```yaml
---
name: writer
description: 보고서, 기획서, 문서를 전문적으로 작성
tools: Read, Write, Edit, Glob
model: sonnet
---
당신은 기술 문서 및 비즈니스 문서 전문 작가입니다.

## 원칙
- 독자가 누구인지 먼저 확인
- 핵심 메시지를 먼저 전달 (피라미드 구조)
- 불필요한 수식어 제거
- 근거 없는 주장 금지

## 문서 유형별 구조
- 보고서: 요약 → 배경 → 분석 → 결론 → 액션 아이템
- 기획서: 문제 정의 → 해결책 → 실행 계획 → 기대 효과
- 분석문: 현상 → 원인 → 영향 → 대응
```

**`.claude/agents/planner.md`** — 작업 분해/계획 전담:
```yaml
---
name: planner
description: 복잡한 작업을 실행 가능한 단계로 분해
tools: Read, Glob, Grep
model: sonnet
---
당신은 프로젝트 플래너입니다.

## 작업 방식
1. 최종 목표를 명확히 정의
2. 역순으로 필요한 단계를 도출
3. 각 단계의 의존성 파악
4. 병렬 처리 가능한 작업 식별
5. 체크리스트 형태로 출력

## 출력 형식
- [ ] 단계 1: [설명] (예상 소요: X)
  - 의존성: 없음
  - 담당: [메인/researcher/writer]
- [ ] 단계 2: ...
```

### 0-3. 핵심 훅 세팅

해커톤 우승자의 핵심 인사이트: **훅은 "언제" 개입할지를 자동화한다.**

`.claude/settings.json`에 추가할 최소 훅:
```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "echo '✅ 파일 수정됨 — git diff로 변경 확인 가능'"
          }
        ]
      }
    ],
    "Stop": [
      {
        "type": "command",
        "command": "echo '🏁 작업 완료 — 결과물을 확인하세요'"
      }
    ]
  }
}
```

> [!warning] 컨텍스트 경제학 — 해커톤 우승자의 핵심 교훈
> **도구가 많을수록 성능이 떨어진다.** MCP와 플러그인을 모두 켜면 200K 중 실사용 가능 컨텍스트가 70K까지 줄 수 있다. **경험적 규칙: 동시 활성화 MCP 5~6개, 플러그인 4~5개, 총 도구 80개 미만.** 지금 이 작업에 필요한 것만 켜고 나머지는 꺼두는 것이 핵심이다.

### 0-4. 컨텍스트 절약을 위한 스킬 구성

자주 쓰는 워크플로우를 스킬로 만들면, 매번 프롬프트를 길게 쓸 필요가 없다.

**`~/.claude/skills/deep-research/SKILL.md`**:
```yaml
---
name: deep-research
description: 주제에 대한 심층 리서치를 수행할 때 사용
---
# 심층 리서치 프로토콜

1. researcher 서브에이전트에게 초기 조사 위임
2. 결과를 받아서 핵심 발견 정리
3. 추가 조사가 필요한 부분 식별
4. 최종 보고서를 writer 서브에이전트에게 위임하여 정리
5. 결과물을 지정된 경로에 저장
```

**`~/.claude/skills/structured-doc/SKILL.md`**:
```yaml
---
name: structured-doc
description: 구조화된 문서(보고서, 기획서, 분석문)를 작성할 때 사용
---
# 구조화 문서 작성 프로토콜

1. 먼저 독자와 목적을 확인 (불명확하면 질문)
2. 개요(outline)를 먼저 작성하여 승인 받기
3. 승인 후 섹션별로 작성
4. 작성 완료 후 자기 검토:
   - 핵심 메시지가 명확한가?
   - 근거가 충분한가?
   - 불필요한 부분이 없는가?
5. 9/10 미만이면 개선 후 제출
```

## Phase 1: 작업 시작 — 매 작업의 첫 3분

> [!important] 핵심 습관
> **무턱대고 요청하지 않는다.** 매 작업을 시작할 때 이 체크리스트를 따른다. 이것이 "감으로 쓰는 사람"과 "전문가"의 가장 큰 차이다.

### 1-1. 작업 유형 판별

```
내가 하려는 작업은?
├── 리서치/분석 → Phase 2-A로
├── 문서 작성 → Phase 2-B로
├── 에이전트/자동화 구축 → Phase 2-C로
└── 복합 작업 (위 2개 이상 조합) → Phase 2-D로
```

### 1-2. 컨텍스트 준비 체크리스트

```
□ 이 작업에 필요한 MCP만 켜져 있는가? (불필요한 것은 끄기)
□ 관련 파일/문서가 있다면, 경로를 파악했는가?
□ 최종 결과물의 형태가 명확한가? (파일? 보고서? 코드?)
□ 작업 범위가 하나의 컨텍스트 윈도우에 들어가는가?
   → 안 들어가면 Phase 2-D (멀티 세션 전략) 적용
```

### 1-3. 프롬프트 구조화

중급 수준에서 고급으로 올라가는 핵심: **XML 태그로 구조 잡기**.

매 작업의 첫 프롬프트 템플릿:
```xml
<context>
[배경 상황 — 왜 이 작업이 필요한지]
</context>

<task>
[구체적으로 해야 할 일]
</task>

<constraints>
[제약 조건, 주의사항]
</constraints>

<output>
[원하는 결과물의 형태와 저장 위치]
</output>
```

> [!tip] 프로 팁
> "왜"를 포함하면 Claude가 맥락을 파악해서 더 적절한 판단을 내린다. "API 문서를 작성해줘"보다 "신규 입사자 온보딩을 위해 API 문서를 작성해줘"가 훨씬 좋은 결과를 낸다.

## Phase 2-A: 리서치/분석 워크플로우

### 단순 리서치 (30분 이내)

```
1. 직접 요청 (서브에이전트 불필요)
   
   <context>
   [조사 배경]
   </context>
   
   <task>
   [조사할 주제]에 대해 조사해줘.
   </task>
   
   <output>
   다음 구조로 정리:
   - 핵심 발견 (5줄)
   - 상세 분석
   - 불확실한 부분은 "확인 필요"로 표시
   - 출처
   </output>

2. 결과 확인 → 추가 질문 → 완성
```

### 심층 리서치 (1시간+)

```
1. planner 서브에이전트에게 조사 계획 수립 위임
   "researcher 에이전트를 사용해서 [주제]에 대해 심층 조사해줘.
    조사 계획을 먼저 세우고 보여줘."

2. 계획 리뷰 → 승인/수정

3. 실행 (researcher 서브에이전트가 독립 컨텍스트에서 작업)
   → 메인 컨텍스트 보존됨!

4. 결과 수령 → 추가 방향 지시 또는 완성

5. 필요시 writer 서브에이전트에게 최종 정리 위임
```

> [!tip] 컨텍스트 절약의 핵심
> 서브에이전트를 쓰는 가장 큰 이유는 **메인 컨텍스트를 보호**하는 것이다. researcher가 웹 100페이지를 뒤져도, 메인에는 요약만 돌아온다. 해커톤 우승자: *"Subagent의 핵심 장점은 컨텍스트 보존이다. 메인 에이전트의 컨텍스트 윈도우를 복잡한 하위 작업이 점유하지 않는다."*

## Phase 2-B: 문서 작성 워크플로우

### 체이닝 패턴 (모든 문서에 적용)

**절대 한 번에 전체 문서를 요청하지 않는다.** 단계별 체이닝이 품질을 결정한다.

```
[Step 1: 개요]
"다음 문서의 개요(outline)를 작성해줘.

<context>[배경]</context>
<audience>[독자]</audience>
<purpose>[목적]</purpose>
<format>[문서 유형: 보고서/기획서/분석문]</format>"

↓ 개요 확인 & 피드백 ↓

[Step 2: 본문 작성]
"승인한 개요대로 본문을 작성해줘.
 섹션 [1~3]부터 시작."

↓ 확인 & 피드백 ↓

[Step 3: 나머지 + 자기 검토]
"나머지 섹션을 완성하고,
 전체를 리뷰해서 9/10 이상의 품질이 되도록 다듬어줘.
 부족한 부분이 있으면 스스로 개선해."

↓ 최종 확인 ↓

[Step 4: 포맷팅]
"최종본을 [docx/md/pdf] 파일로 만들어줘."
```

### 창의적 문서가 필요할 때

AI의 전형적이고 뻔한 결과물을 피하려면:

```xml
<task>
[문서 주제]
</task>

<creative_direction>
전형적인 [장르/형식]의 클리셰를 피해줘.
먼저 3가지 서로 다른 접근 방식을 제안하고,
각각의 장단점을 분석해줘.
내가 선택하면 그 방향으로 작성해.
</creative_direction>
```

또는 Verbalized Sampling 적용:
```
이 주제에 대해 5가지 서로 다른 관점의 개요를 만들어줘.
각각이 얼마나 "전형적"인지 1-10으로 평가해줘
(1 = 매우 독특, 10 = 매우 전형적).
가장 낮은 점수의 것을 발전시키고 싶어.
```

## Phase 2-C: 자동화/에이전트 구축 워크플로우

### 새 서브에이전트 만들기

```
1. 메타 프롬프팅으로 시작:
   "다음 작업을 전담할 서브에이전트를 설계해줘.
    
    <purpose>[에이전트의 목적]</purpose>
    <scope>[접근할 수 있어야 하는 도구들]</scope>
    <constraints>[제한해야 하는 것들]</constraints>
    
    .claude/agents/ 디렉토리에 마크다운 파일로 생성해줘."

2. 테스트:
   "방금 만든 [에이전트명] 에이전트를 사용해서
    [간단한 테스트 작업]을 수행해줘."

3. 결과 확인 → 에이전트 프롬프트 반복 개선
```

### 새 훅 만들기

```
"다음 시점에 자동으로 실행되는 훅을 만들어줘.

<trigger>[언제: PreToolUse/PostToolUse/Stop 중 선택]</trigger>
<condition>[어떤 조건에서]</condition>
<action>[무엇을 실행]</action>

.claude/settings.json에 추가해줘."
```

### 새 스킬 만들기

```
"다음 워크플로우를 스킬로 만들어줘.

<workflow>
[워크플로우 설명]
</workflow>

<trigger_description>
[Claude가 언제 이 스킬을 자동으로 발동시킬지 — 
 이 설명이 스킬 발견의 핵심이므로 명확하게]
</trigger_description>

~/.claude/skills/[이름]/SKILL.md로 생성해줘."
```

> [!warning] 해커톤 우승자 교훈: 계층의 분업
> - **Skills** = "무엇을" (원칙과 절차)
> - **Hooks** = "언제" (자동 개입 시점)
> - **Subagents** = "누가" (역할 분리)
> 
> 이 세 계층이 맞물려야 자동화가 작동한다. 하나만 쓰면 반쪽짜리다.

## Phase 2-D: 복합/대규모 작업 — 멀티 세션 전략

하나의 컨텍스트 윈도우로 끝나지 않는 작업일 때.

### 전략 1: 첫 세션과 이후 세션을 다르게 쓰기

Anthropic 공식 권장 패턴:

```
[첫 번째 세션]
"이 프로젝트의 요구사항을 분석하고:
 1. progress.txt에 전체 작업 목록 작성
 2. 우선순위 정렬
 3. 첫 번째 작업 착수"

[이후 세션]
"progress.txt를 읽고 이어서 작업해줘.
 완료된 항목은 체크하고, 다음 미완료 항목을 진행해줘."
```

### 전략 2: 병렬 분리 (해커톤 우승자 패턴)

```
판단 기준: 작업들이 서로 다른 파일을 건드리는가?

YES → /fork로 대화 분기
      세션 A: [작업 A]
      세션 B: [작업 B]
      
더 확실한 분리 필요 → Git Worktree
      git worktree add ../feature-a feature-a
      각 worktree에서 별도 Claude 인스턴스 실행

역할이 다른 작업 → Subagent 위임
      메인: 전체 관리
      researcher: 조사 담당
      writer: 문서 작성 담당
```

> [!important] 병렬화의 전제조건
> **"먼저 나누고, 그 다음 동시에"** — 범위가 겹치면 병렬이 불가능하다.
> - /fork: 대화 세션 분리 (비중첩 작업일 때만)
> - Worktree: 파일 시스템 분리 (충돌 불가능 상태)
> - Subagent: 역할과 권한 분리

## Phase 3: 작업 중 — 품질을 올리는 습관들

### 3-1. 결과가 뻔할 때 (Mode Collapse 대응)

```
시도 1: "전형적인 답변 말고, 가장 독창적인 접근을 보여줘"

시도 2: "이 주제에 대해 3가지 서로 다른 관점을 제시하고,
        각각의 독창성을 1-10으로 자기 평가해줘"

시도 3: "다음 세 전문가라면 각각 어떻게 접근할까?
        - [분야 A 전문가]
        - [분야 B 전문가]  
        - [완전히 다른 분야 전문가]"
```

### 3-2. 결과 품질이 떨어질 때

```
체크 1: 컨텍스트가 과부하인가?
        → /compact로 압축하거나 새 세션 시작
        
체크 2: 프롬프트가 모호한가?
        → XML 태그로 구조화, "왜"를 추가
        
체크 3: 작업이 너무 큰가?
        → 체이닝으로 분할
        
체크 4: MCP/플러그인을 너무 많이 켰는가?
        → 불필요한 것 끄기 (컨텍스트 경제학!)
```

### 3-3. 장시간 작업 시 컨텍스트 관리

```
20분마다 자기 점검:
- Claude가 이전 결정을 기억하고 있는가?
- 답변의 일관성이 유지되는가?
- 같은 것을 반복 설명하고 있지는 않은가?

위 중 하나라도 YES → 컨텍스트 관리 필요:
1. "지금까지의 핵심 결정사항을 요약해줘" (상태 확인)
2. 필요시 /compact
3. 핵심 맥락을 progress.txt에 기록
```

## Phase 4: 작업 완료 — 자산화

### 4-1. 반복될 작업이면 자산화

```
이 작업을 또 하게 될까?
├── YES → 스킬 또는 슬래시 커맨드로 만들기
│        "방금 한 작업의 워크플로우를 
│         ~/.claude/skills/[이름]/SKILL.md로 만들어줘"
│
├── 부분적으로 → CLAUDE.md에 패턴 추가
│        "이번에 발견한 [패턴/규칙]을 
│         CLAUDE.md에 추가해줘"
│
└── NO → 그냥 넘어가기
```

### 4-2. 실패에서 배우기

```
Claude가 기대에 못 미치는 결과를 냈을 때:

1. 원인 분석:
   - 프롬프트가 모호했는가?
   - 컨텍스트가 부족했는가?
   - 작업이 너무 컸는가?
   - 잘못된 도구/에이전트를 사용했는가?

2. CLAUDE.md 또는 에이전트 프롬프트에 교훈 반영:
   "이번 작업에서 [문제]가 발생했어.
    앞으로 [예방 규칙]을 CLAUDE.md에 추가해줘."
```

> [!quote] 해커톤 우승자의 핵심 통찰
> *"자동화를 도구로 보면 '이 도구가 저 작업을 빠르게 해준다'에서 사고가 멈춘다. 자동화를 계층으로 보면 '이 작업 전체를 어떻게 구조화할 것인가'로 질문이 확장된다. 속도의 개선은 부수적이다. 진짜 가치는 작업의 재정의에 있다."*

## 빠른 참조 카드

### 작업 시작 전 3초 체크

```
1. 필요한 MCP만 켜져 있나? (5~6개 이하)
2. XML 태그로 구조 잡았나? (context/task/output)
3. 한 번에 끝날 규모인가? (아니면 분할)
```

### 프롬프트 품질 체크

```
□ "왜" 필요한지 맥락이 있는가?
□ 결과물의 형태가 명시되어 있는가?
□ 예시가 있으면 더 좋겠는가? (있으면 추가)
□ 제약 조건이 명시되어 있는가?
□ 행동 동사를 썼는가? ("제안해줘" vs "만들어줘")
```

### 문제 발생 시 대응 맵

```
결과가 뻔함 → Verbalized Sampling / 다중 관점 요청
결과가 부정확 → CoT 추가 / 자기 검증 요청
결과가 중간에 끊김 → 컨텍스트 과부하 → /compact 또는 분할
결과가 이전과 모순 → 컨텍스트 관리 → progress.txt 동기화
너무 장황함 → "간결하게" 명시 또는 출력 형식 제한
너무 소극적 → "적극적으로 실행해줘, 제안이 아니라 구현"
```
