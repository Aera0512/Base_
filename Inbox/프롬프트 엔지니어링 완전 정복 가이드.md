# 프롬프트 엔지니어링 완전 정복 가이드

> [!abstract] 핵심 철학
> 프롬프트 엔지니어링은 "AI에게 말을 잘 거는 것"이 아니라, **"단어로 기계를 프로그래밍하는 것"**(Ethan Mollick, MIT)이다. AI의 잠재력을 억제하지 않으면서 원하는 결과를 정밀하게 이끌어내는 기술이며, 2025년 현재 **컨텍스트 엔지니어링**이라는 더 넓은 개념으로 확장되고 있다.

---

## 1. 왜 프롬프트 엔지니어링이 중요한가

LLM은 본질적으로 **예측 엔진**이다. 입력된 텍스트 시퀀스를 기반으로 다음 토큰을 예측하는데, 프롬프트가 바로 이 예측의 방향을 결정하는 "초기 조건"이다. 같은 모델이라도 프롬프트에 따라 완전히 다른 품질의 결과가 나온다.

**프롬프트를 잘못 쓰면 일어나는 일:**
- 모호하거나 부정확한 응답
- 여러 번의 수정 대화 필요 (시간과 토큰 낭비)
- AI의 실제 능력보다 한참 못 미치는 결과물
- 할루시네이션(허위 정보 생성) 증가

**프롬프트를 잘 쓰면 일어나는 일:**
- 한 번에 원하는 결과물 획득 (one-shot)
- AI의 잠재력에 가까운 품질
- 재현 가능한 일관된 출력
- 비용과 시간 절약

> [!tip] 핵심 통찰
> Anthropic 공식 문서: "Claude를 **능력은 뛰어나지만 당신의 맥락을 전혀 모르는 새로 온 천재 인턴**이라고 생각하라. 정확하게 설명할수록 결과가 좋아진다."

## 2. 기초 테크닉: 모든 프롬프트의 빌딩 블록

### 2-1. 명확하고 직접적으로 말하기 (Be Clear and Direct)

가장 기본이면서 가장 중요한 원칙. Claude 4.x 모델들은 **정밀한 지시 따르기(precise instruction following)** 에 특화 훈련되어 있어서, 구체적으로 말할수록 좋다.

> [!example] 비교 예시
> **나쁜 프롬프트:**
> "마케팅 전략 짜줘"
> 
> **좋은 프롬프트:**
> "B2B SaaS 스타트업의 시리즈 A 단계 마케팅 전략을 짜줘. 월 예산 500만원, 주 타겟은 중소기업 IT 담당자. 콘텐츠 마케팅과 LinkedIn 광고를 중심으로, 3개월 로드맵을 포함해줘. 각 월별 KPI와 예상 비용 분배도 넣어줘."

**핵심 원칙들:**
- **목표를 명시하라**: "왜" 필요한지 맥락을 주면 Claude가 더 적절한 판단을 내림
- **행동을 명시하라**: "변경 사항을 제안해줘" vs "이 함수를 변경해줘" — 후자가 실제 실행을 유도
- **제약 조건을 명시하라**: 길이, 톤, 형식, 포함/제외 사항
- **"Above and beyond" 행동을 원하면 명시적으로 요청하라**: Claude 4.x는 요청된 것만 하려는 경향이 있으므로, 풍부한 결과를 원하면 "가능한 한 완성도 높게, 기본을 넘어서는 구현을 해줘"라고 말하기

### 2-2. 구조화된 프롬프트 (Structured Prompts)

복잡한 요청일수록 구조가 중요하다. Anthropic은 **10가지 컴포넌트 프레임워크**를 권장한다.

```
1. Task Context (역할과 과제) — WHO, WHAT
2. Tone Context (톤 설정) — 어떤 분위기로
3. Background Data (배경 데이터) — 참고할 정보
4. Detailed Task Description (상세 과제 설명)
5. Examples (예시) — 원하는 결과물의 모습
6. Conversation History (대화 맥락) — 이전 대화 참조
7. Immediate Task (즉시 수행할 작업)
8. Output Format (출력 형식 지정)
9. Precognition (사전 추론 요청) — "먼저 분석한 뒤 답하라"
10. Constraints (제약 조건)
```

> [!example] 10가지 컴포넌트 적용 예시
> ```
> [Task Context]
> 당신은 10년 경력의 UX 리서처입니다.
> 
> [Tone]
> 전문적이지만 팀원에게 설명하듯 친근하게.
> 
> [Background]
> 우리 앱은 건강 관리 앱이고, 최근 온보딩 이탈률이 40%입니다.
> DAU는 5만, MAU는 15만입니다.
> 
> [Task]
> 온보딩 개선을 위한 사용자 리서치 계획을 작성해주세요.
> 
> [Output Format]
> 1. 리서치 목표 (3줄 이내)
> 2. 방법론 (인터뷰/서베이/A/B테스트 등)
> 3. 참여자 기준
> 4. 타임라인 (2주 이내)
> 5. 예상 산출물
> 
> [Constraints]
> - 예산: 300만원 이내
> - 리서치 기간: 2주
> - 원격 진행만 가능
> ```

### 2-3. XML 태그 — Claude의 특수 무기

Claude는 XML 태그를 인식하도록 **특별히 훈련**되어 있다. 다른 LLM에서는 마크다운이 더 효과적일 수 있지만, Claude에서는 XML 태그가 최고의 구조화 도구다.

**왜 XML 태그인가:**
- **명확성**: 프롬프트의 각 부분을 명확히 분리
- **정확성**: Claude가 지시를 예시로, 맥락을 과제로 혼동하는 것을 방지
- **유연성**: 프롬프트의 일부만 쉽게 수정 가능
- **파싱 가능성**: Claude의 출력에도 XML 태그를 요청하면 후처리가 쉬움

> [!example] XML 태그 활용 예시
> ```xml
> <role>시니어 보안 엔지니어</role>
> 
> <context>
> Node.js Express 기반 REST API.
> 현재 JWT 인증 사용 중.
> 최근 보안 감사에서 3가지 취약점 발견.
> </context>
> 
> <vulnerabilities>
> 1. SQL 인젝션 가능성 - user 검색 엔드포인트
> 2. CORS 설정 과도하게 permissive
> 3. Rate limiting 미적용
> </vulnerabilities>
> 
> <task>
> 각 취약점에 대해:
> 1. 위험도 평가 (Critical/High/Medium/Low)
> 2. 구체적인 공격 시나리오
> 3. 수정 코드
> 4. 테스트 방법
> </task>
> 
> <output_format>
> 취약점별로 섹션을 나누고, 수정 전/후 코드를 diff 형태로 보여줘.
> </output_format>
> ```

**파워 유저 팁**: XML 태그를 다른 테크닉(Few-shot의 `<examples>`, CoT의 `<thinking>` + `<answer>`)과 조합하면 초고성능 프롬프트를 만들 수 있다.

## 3. 추론 강화 테크닉: AI가 "생각"하게 만들기

### 3-1. Chain of Thought (CoT) — 단계적 추론

LLM에게 **단계별로 생각하라고 명시적으로 지시**하는 기법. 복잡한 추론, 수학, 논리 문제에서 정확도를 크게 향상시킨다.

**원리:** LLM은 한 번에 답을 내리면 중간 과정을 건너뛰고 "직감"으로 답하게 되는데, 단계별 추론을 강제하면 각 단계에서 오류를 잡을 수 있다.

> [!example] CoT 적용 예시
> **CoT 없이:**
> "내가 6살일 때 언니는 나이의 절반이었어. 내가 70살이면 언니는 몇 살이야?"
> → AI 답변: "35살" (오답!)
> 
> **CoT 적용:**
> "단계별로 생각해봐. 내가 6살일 때 언니는 나이의 절반이었어. 내가 70살이면 언니는 몇 살이야?"
> → AI 답변: "6살일 때 언니는 3살 → 나이 차이는 3살 → 내가 70이면 언니는 67살" (정답!)

**Claude에서의 CoT 사용법:**

```xml
<instructions>
다음 문제를 풀어줘.
답을 내기 전에 <thinking> 태그 안에서 단계별로 추론해줘.
최종 답은 <answer> 태그에 넣어줘.
</instructions>

<problem>
한 회사가 첫 해에 200명을 고용했다.
둘째 해에는 전년 대비 30% 증가했다.
셋째 해에는 둘째 해 대비 20% 감소했다.
현재 총 직원 수는?
</problem>
```

**Extended Thinking (확장 사고) — Claude의 내장 CoT:**

Claude 4.x에는 확장 사고 모드가 있다. 이 모드에서는 오히려 **명시적 CoT 지시를 제거하고**, 일반적이고 높은 수준의 지시만 주는 것이 좋다.

```
❌ "단계별로 생각해봐" (확장 사고 모드에서는 불필요)
✅ "이 문제를 깊이 분석해줘" (자연스러운 지시)
```

### 3-2. Tree of Thoughts (ToT) — 가지치기 탐색

CoT가 **하나의 추론 경로**를 따르는 것이라면, ToT는 **여러 추론 가지를 동시에 탐색**하고 각각을 평가한 뒤 최선을 선택하는 기법이다.

**원리:** 복잡한 문제는 하나의 사고 경로만으로는 최적해에 도달하기 어렵다. 여러 접근법을 동시에 탐색하고, 막다른 길이면 되돌아가는 것(backtracking)이 가능하다.

> [!example] ToT 프롬프트 예시
> ```
> 다음 문제에 대해 3가지 서로 다른 접근 방식을 제시해줘.
> 각 접근 방식의 장단점을 분석하고, 가장 효과적인 것을 선택해서 상세히 전개해줘.
> 
> 문제: "일 평균 방문자 1000명인 블로그의 수익화 전략"
> 
> 접근 방식 1: [제시]
> - 장점: ...
> - 단점: ...
> - 실현 가능성 점수: /10
> 
> 접근 방식 2: [제시]
> ...
> 
> 접근 방식 3: [제시]
> ...
> 
> 최종 선택: [가장 높은 점수의 접근 방식을 상세 전개]
> ```

**활용 상황:** 창의적 문제 해결, 전략 수립, 설계 결정 등 "정답이 하나가 아닌" 문제에 특히 효과적.

### 3-3. Self-Consistency — 다수결 추론

같은 문제에 대해 **여러 번의 독립적 추론**을 수행하고, **가장 자주 나온 답**을 최종 답으로 선택하는 기법.

**원리:** 하나의 추론 경로는 오류를 포함할 수 있지만, 여러 독립 경로에서 같은 답이 나온다면 그 답이 맞을 확률이 높다.

> [!example] Self-Consistency 적용 예시
> ```
> 다음 문제를 3가지 서로 다른 방법으로 풀어줘.
> 각 방법의 추론 과정을 보여주고, 최종적으로 가장 일관된 답을 선택해줘.
> 
> 문제: "어떤 가게에서 사과를 30% 할인해서 팔고 있다. 
> 할인 전 가격이 5000원이었고, 추가로 회원 할인 10%가 적용된다면
> 최종 가격은?"
> 
> 방법 1: [순차 할인 계산]
> 방법 2: [총 할인율 계산 후 적용]
> 방법 3: [역산으로 검증]
> 
> 일관성 검증: 세 방법의 답이 일치하는지 확인
> ```

### 3-4. ReAct — 추론 + 행동의 결합

**Reasoning(추론)**과 **Acting(행동)**을 인터리브(교차)하는 패턴. AI가 생각하고, 행동하고(검색, 계산 등), 관찰 결과를 기반으로 다시 생각하는 루프를 형성한다.

**Thought → Action → Observation → Thought → Action → ...**

이것은 Claude가 도구(웹 검색, 코드 실행 등)를 사용할 때 자연스럽게 따르는 패턴이기도 하다.

> [!example] ReAct 패턴 프롬프트
> ```
> 다음 질문에 답하기 위해 생각-행동-관찰 패턴을 따라가줘.
> 
> 질문: "현재 한국에서 가장 많이 사용되는 프로그래밍 언어는?"
> 
> Thought 1: 이 질문에 답하려면 최신 통계 데이터가 필요하다.
> Action 1: [웹 검색: "한국 프로그래밍 언어 순위 2025"]
> Observation 1: [검색 결과]
> Thought 2: 검색 결과를 보니 여러 출처가 있다. 
>             가장 신뢰할 수 있는 출처를 기준으로 정리하자.
> Action 2: [해당 출처 상세 확인]
> Observation 2: [상세 데이터]
> Thought 3: 충분한 데이터를 확보했으니 답변을 구성하자.
> Final Answer: ...
> ```

## 4. 창의력 극대화 테크닉: AI의 잠재력을 억제하지 않기

### 4-1. Mode Collapse 문제 이해하기

> [!warning] 핵심 문제
> LLM은 RLHF(인간 피드백 기반 강화학습) 과정에서 **"안전하고 전형적인" 답변**을 선호하도록 훈련된다. 인간은 익숙하고 전형적인 답변을 "더 좋다"고 평가하는 경향이 있기 때문이다. 이것이 **mode collapse** — AI가 창의적이고 다양한 가능성을 가지고 있음에도 항상 비슷한 패턴의 답을 내놓는 현상이다.

**이것은 모델의 능력 부족이 아니라 "억제"다.** 기본 사전학습 모델에는 풍부한 다양성이 존재하지만, 정렬(alignment) 과정이 이를 억누르는 것이다.

### 4-2. Verbalized Sampling — 최신 연구 기반 창의력 해방

2025년 10월 발표된 연구(Verbalized Sampling)에서 발견된 기법. **단 한 문장을 추가하면 AI의 창의적 다양성이 2.1배까지 증가**한다.

**원리:** AI에게 단일 "최선의 답"을 요구하는 대신, **여러 가능한 답과 각각의 확률을 말로 표현(verbalize)**하도록 요청한다. 이것이 정렬로 인한 억제를 우회한다.

> [!example] Verbalized Sampling 실전 프롬프트 10가지
> 
> **1. 확률 분포 요청:**
> ```
> 아래 질문에 대해 5가지 서로 다른 답변을 생성해줘.
> 각 답변에 대해 네가 이것을 생성할 가능성을 1-10으로 평가해줘.
> 그 중 하나를 내가 선택할게.
> 
> 질문: [당신의 과제]
> ```
> 
> **2. "만약 10번 답한다면":**
> ```
> 이 질문에 10번 답한다면, 가장 일반적인 답과 
> 가장 드물지만 흥미로운 답은 각각 무엇일까?
> 둘 다 보여줘.
> ```
> 
> **3. 의도적 비전형성 요청:**
> ```
> 이 주제에 대한 "전형적인" 답변은 이미 알고 있어.
> 대신 대부분의 사람들이 생각하지 못할 독창적인 접근법을 제시해줘.
> ```
> 
> **4. 페르소나 분산:**
> ```
> 이 문제에 대해 다음 세 사람이 각각 어떻게 접근할지 답해줘:
> - 엘론 머스크 (first principles 사고)
> - 무라카미 하루키 (은유적 사고)
> - 마리 콘도 (정리의 관점)
> ```
> 
> **5. 자기 검열 해제:**
> ```
> "전형적으로 좋은" 답변을 하려는 경향을 잠시 내려놓고,
> 가장 대담하고 색다른 아이디어를 자유롭게 브레인스토밍해줘.
> 실현 가능성은 나중에 따져볼 테니 우선 가능성의 폭을 넓혀줘.
> ```

**연구 결과:** 이 기법을 창작 글쓰기에 적용했을 때, "안녕 없이(Without a goodbye)"라는 주제에서 일반 프롬프팅은 전형적인 이별 장면만 나왔지만, Verbalized Sampling으로는 우주적 사건, 무음의 이메일, 춤 중간에 멈추는 음악 등 훨씬 풍부한 내러티브가 나왔다.

### 4-3. 창의성과 제어의 균형 잡기

> [!important] 핵심 딜레마
> 제약이 너무 많으면 → AI의 창의력 억제
> 제약이 너무 적으면 → AI가 원하지 않는 방향으로 갈 위험
> 
> **해답: "가드레일은 좁게, 놀이터는 넓게"**

**실전 전략:**

```
✅ 좋은 접근: "형식은 이렇게 맞추되, 내용은 자유롭게"
❌ 나쁜 접근: "이런 내용을 이런 순서로 이런 톤으로 이런 단어를 써서"

✅ 좋은 접근: "한국 중소기업 HR 담당자 관점의 글 (나머지는 자유)"
❌ 나쁜 접근: "500자, 3단락, 첫 문장은 질문으로 시작, 마지막은 CTA"
```

**Temperature와 Top-P 가이드 (API 사용 시):**

| 목적 | Temperature | Top-P | 설명 |
|------|------------|-------|------|
| 기술 문서, 코드, 팩트 | 0 ~ 0.2 | 0.1 ~ 0.3 | 결정론적, 일관성 최대 |
| 비즈니스 글쓰기, 분석 | 0.5 ~ 0.7 | 0.5 ~ 0.7 | 균형잡힌 창의성 |
| 브레인스토밍, 창작 | 0.8 ~ 1.0 | 0.8 ~ 1.0 | 최대 다양성 |

### 4-4. 자기 평가(Self-Evaluation) — AI가 스스로 품질을 올리게 하기

AI 엔지니어들이 실무에서 발견한 강력한 패턴: **AI에게 자기 답변을 평가하고, 기준 이하면 재시도하게 만든다.**

> [!example] 자기 평가 패턴
> ```
> 다음 과제를 수행해줘: [과제 설명]
> 
> 답변 후, 스스로 1-10점으로 평가해줘.
> 9점 미만이면, 무엇이 부족한지 설명하고 개선된 버전을 다시 작성해줘.
> 더 잘 할 수 있다면 반드시 개선해줘.
> ```

**왜 효과적인가:** LLM은 인간처럼 "가장 쉬운 답"을 먼저 내놓는 경향이 있다. 명시적 품질 기준을 주면, 더 깊이 있는 사고를 유도한다.

## 5. Few-Shot Prompting: 예시의 과학

### 5-1. Zero-Shot vs Few-Shot

| 유형 | 설명 | 적합한 상황 |
|------|------|-------------|
| **Zero-shot** | 예시 없이 지시만 제공 | 단순하고 명확한 작업 |
| **One-shot** | 예시 1개 제공 | 형식/톤을 보여주고 싶을 때 |
| **Few-shot** | 예시 2~5개 제공 | 패턴이 복잡하거나 일관성이 중요할 때 |

### 5-2. 효과적인 Few-Shot의 원칙

1. **예시는 형용사 열 개보다 낫다**: "간결하고 전문적인 톤으로"보다 실제 예시 하나가 더 효과적
2. **좋은 예시 + 나쁜 예시**: 원하는 것과 원하지 않는 것의 경계를 보여줌
3. **과하지 않게**: 예시가 너무 많으면 AI가 예시를 그대로 복제하려 해서 오히려 창의성이 줄어듦. 보통 2~3개가 최적
4. **대표성 있는 예시**: 엣지 케이스나 특수한 경우가 아닌, 전형적인 사례를 선택

> [!example] Few-Shot + 네거티브 예시
> ```xml
> <task>
> 제품 리뷰를 3줄 요약으로 변환해줘.
> </task>
> 
> <examples>
> <good_example>
> 입력: "이 노트북은 정말 가볍고 배터리가 오래 가요. 
>        다만 키보드가 좀 얕아서 타이핑감은 아쉽습니다. 
>        가격 대비 성능은 만족스럽습니다."
> 출력: "경량 디자인과 긴 배터리가 강점. 
>        키보드 깊이감은 부족하나, 가성비 만족도 높음. 
>        모바일 작업 위주 사용자에게 추천."
> </good_example>
> 
> <bad_example>
> 이런 식은 안 됨:
> "이 노트북은 좋습니다. 가볍습니다. 추천합니다."
> (이유: 원문의 구체적 장단점이 사라지고 너무 피상적)
> </bad_example>
> </examples>
> ```

### 5-3. Claude 특화 팁: 예시와 행동의 일관성

> [!warning] Anthropic 공식 경고
> Claude 4.x는 예시의 세부사항에 매우 주의를 기울인다. 예시에 포함된 행동은 **격려하고 싶은 행동만** 넣어야 한다. 예시 안에 원치 않는 패턴이 있으면 Claude가 그것까지 학습해서 재현할 수 있다.

## 6. 역할 부여(Role Prompting): 페르소나의 힘

### 6-1. 왜 역할이 효과적인가

AI에게 특정 역할을 부여하면, 그 역할의 **어휘, 톤, 사고 방식, 전문 지식**이 모두 활성화된다. "범용 도구"에서 "가상 전문가"로 변환되는 것이다.

### 6-2. 효과적인 역할 설정 전략

**단순 역할:**
```
당신은 시니어 프론트엔드 개발자입니다.
```

**디테일한 역할 (더 효과적):**
```
당신은 Google에서 10년간 근무한 시니어 프론트엔드 개발자입니다.
React와 TypeScript를 주로 사용하며, 성능 최적화와 접근성(a11y)에 
특히 관심이 깊습니다. 코드 리뷰 시 항상 "왜 이렇게 하는지" 
설명을 곁들이는 멘토링 스타일입니다.
```

**다중 페르소나 활용:**
```
이 비즈니스 아이디어를 다음 세 가지 관점에서 각각 평가해줘:

1. 투자자 관점: 투자 매력도, ROI 예상, 리스크
2. 사용자 관점: 실제 필요성, 사용성, 대안 존재 여부
3. 개발자 관점: 기술적 실현 가능성, 구현 복잡도, 확장성
```

### 6-3. Claude의 시스템 프롬프트

API나 프로젝트에서 `system` 파라미터로 역할을 설정하면, 모든 대화에 일관되게 적용된다.

```python
message = client.messages.create(
    model="claude-opus-4-6",
    system="당신은 금융 데이터 분석 전문가입니다. "
           "항상 데이터 기반으로 답하고, 불확실한 부분은 명시합니다. "
           "한국 금융시장에 특화된 지식을 가지고 있습니다.",
    messages=[{"role": "user", "content": "..."}]
)
```

## 7. 프롬프트 체이닝(Prompt Chaining): 복잡한 작업의 분할 정복

### 7-1. 왜 체이닝이 필요한가

한 번의 프롬프트로 모든 것을 처리하면:
- 각 단계의 품질이 떨어짐
- 오류가 전파됨
- 어디서 잘못됐는지 파악하기 어려움
- 컨텍스트가 과부하됨

### 7-2. 체이닝 패턴들

**순차 체이닝 (Sequential):**
```
단계 1: "이 요구사항을 분석해서 기술 스펙 작성" → 출력 A
단계 2: "이 기술 스펙(A)을 기반으로 데이터 모델 설계" → 출력 B
단계 3: "이 데이터 모델(B)로 API 설계" → 출력 C
단계 4: "이 API(C) 구현" → 최종 결과
```

**검증 체이닝 (Validation):**
```
단계 1: "이 글을 작성해줘" → 초안
단계 2: "이 초안을 비판적으로 리뷰해줘. 
        논리적 허점, 누락, 개선점을 찾아줘" → 리뷰
단계 3: "리뷰 내용을 반영해서 최종 버전을 작성해줘" → 최종본
```

**게이트 체이닝 (Gate):**
```
단계 1: "이 코드에 보안 취약점이 있는지 검사해줘" 
         → 취약점 있음/없음
단계 2-A (있으면): "발견된 취약점을 수정해줘"
단계 2-B (없으면): "다음 기능 구현으로 넘어가줘"
```

> [!example] 실전 체이닝: 블로그 포스트 작성
> ```
> 프롬프트 1: 
> "AI 코딩 도구의 미래에 대한 블로그 포스트의 
>  개요(outline)를 작성해줘. 5개 섹션, 각 섹션의 핵심 주장 포함."
> 
> [Claude의 개요 출력]
> 
> 프롬프트 2:
> "이 개요의 섹션 1과 2를 작성해줘. 
>  각 섹션 400-500자, 구체적 사례 포함."
> 
> [Claude의 섹션 1-2 출력]
> 
> 프롬프트 3:
> "이 섹션 1-2를 리뷰해줘. 
>  논리 흐름이 자연스러운지, 주장에 근거가 있는지 확인."
> 
> [Claude의 리뷰 출력]
> 
> 프롬프트 4:
> "리뷰 피드백을 반영해서 섹션 1-2를 수정하고, 
>  이어서 섹션 3-5를 작성해줘."
> ```

## 8. 메타 프롬프팅: AI로 프롬프트를 만들기

### 8-1. 개념

**"프롬프트를 쓰는 프롬프트"** — AI에게 자신을 위한 최적의 프롬프트를 설계하도록 요청하는 기법. Google DeepMind 엔지니어 Anna Bortsova는 이 기법을 적극 활용하여 Gemini가 Veo 3용 수 페이지짜리 상세 프롬프트를 생성하게 했다.

### 8-2. 실전 메타 프롬프팅 워크플로우

> [!example] 3단계 메타 프롬프팅
> **1단계: 러프한 아이디어 제공**
> ```
> 나는 [과제]를 하고 싶어.
> 이 과제를 너에게 최적으로 수행시키려면 
> 어떤 프롬프트를 써야 할까?
> 프롬프트를 직접 작성해줘.
> ```
> 
> **2단계: 반복 개선**
> ```
> 이 프롬프트를 테스트 입력 3가지로 돌려봐.
> 결과가 마음에 안 드는 부분이 있으면 
> 프롬프트를 수정해줘. 단, 너무 특정 케이스에만 
> 맞추지 말고 범용적인 수정을 해줘.
> ```
> 
> **3단계: 엣지 케이스 통합**
> ```
> 이 프롬프트에서 잘 처리하지 못할 것 같은 
> 엣지 케이스를 3가지 생각해보고, 
> 그것들도 처리할 수 있도록 프롬프트를 보강해줘.
> ```

**핵심 팁:** LLM에게 "프롬프트 수정 전에 먼저 질문을 해서 내 의도를 완전히 파악하라"고 지시하면, 더 정확한 메타 프롬프트가 나온다.

### 8-3. Anthropic의 공식 프롬프트 도구

Anthropic은 Claude Console에서 세 가지 프롬프트 도구를 제공한다:
- **Prompt Generator**: 작업 설명만 주면 최적화된 프롬프트 생성
- **Prompt Templates**: 변수를 포함한 재사용 가능한 프롬프트
- **Prompt Improver**: 기존 프롬프트를 분석하고 개선 제안

## 9. 고급 활용 패턴

### 9-1. Step-Back Prompting — 한 발 물러서서 보기

질문을 바로 던지는 대신, 먼저 더 높은 수준의 질문을 하고, 그 답변을 기반으로 구체적 질문에 접근하는 기법.

> [!example]
> **직접 접근 (덜 효과적):**
> "사용자 이탈률을 줄이려면 어떻게 해야 할까?"
> 
> **Step-Back (더 효과적):**
> ```
> 1단계: "SaaS 제품에서 사용자 이탈의 주요 원인들은 무엇인가?"
> 
> [Claude가 일반적 원인들을 분석]
> 
> 2단계: "이 분석을 기반으로, 우리 앱(건강 관리 앱, 
>         온보딩 이탈 40%)의 이탈률을 줄이기 위한 
>         구체적 전략을 제안해줘."
> ```

### 9-2. Generated Knowledge Prompting — AI가 스스로 지식을 만들어 활용

먼저 AI에게 관련 지식을 생성하게 하고, 그 지식을 프롬프트에 포함시켜서 최종 답변의 품질을 높이는 기법.

> [!example]
> ```
> 1단계: "마이크로서비스 아키텍처에서 서비스 간 통신의 
>         주요 패턴들과 각각의 장단점을 설명해줘."
> 
> [Claude가 지식 생성]
> 
> 2단계: "위의 분석을 참고해서, 현재 모놀리스인 우리 
>         주문 관리 시스템을 마이크로서비스로 전환할 때 
>         가장 적합한 통신 패턴을 추천해줘.
>         배경: 일 주문량 10만건, 결제 연동 필수, 
>         실시간성 요구."
> ```

### 9-3. 제약 기반 창의성 (Constrained Creativity)

역설적으로, **적절한 제약이 오히려 더 창의적인 결과**를 만든다. 완전한 자유보다 "이 범위 안에서 최대한 창의적으로"가 더 효과적이다.

> [!example]
> ```
> ❌ "자유롭게 단편소설을 써줘"
> → 전형적이고 무난한 이야기가 나올 확률 높음
> 
> ✅ "다음 제약 내에서 단편소설을 써줘:
>    - 장르: 일상 SF (지금으로부터 3년 후)
>    - 주인공: AI 번역기를 쓰는 통역사
>    - 갈등: 기술이 자신의 직업을 대체하는 것을 
>      목격하면서도 그 기술에 의존하는 아이러니
>    - 톤: 유머러스하지만 씁쓸한
>    - 길이: 800자 내외
>    - 제약: 대화는 반드시 3개 이상의 언어를 포함"
> → 제약이 창의적 솔루션을 강제하여 더 독특한 결과
> ```

## 10. Claude 특화 기법들

### 10-1. Long Context 전략 (20K+ 토큰)

대량의 문서를 다룰 때:

1. **문서를 앞에, 지시를 뒤에**: 긴 문서 → 구체적 질문 순서로 배치하면 **품질이 30%까지 향상** (Anthropic 공식 데이터)
2. **XML로 구조화**: 여러 문서는 `<document>` 태그로 감싸고 메타데이터 포함
3. **인용 먼저 요청**: "관련 부분을 먼저 인용하고 나서 답해줘" → 노이즈 감소

```xml
<documents>
  <document index="1">
    <source>2024 연간 보고서</source>
    <document_content>...</document_content>
  </document>
  <document index="2">
    <source>경쟁사 분석 리포트</source>
    <document_content>...</document_content>
  </document>
</documents>

<instructions>
위 문서들에서 관련 부분을 먼저 인용한 뒤,
우리 회사와 경쟁사의 핵심 차별점을 분석해줘.
</instructions>
```

### 10-2. 할루시네이션 줄이기

```
- 확실하지 않으면 "모르겠다" 또는 "확인이 필요하다"고 말해줘
- 추측은 명시적으로 "추측:"이라고 표시해줘
- 사실과 의견을 구분해서 답해줘
```

### 10-3. Opus 4.6 특유의 튜닝

Anthropic 공식 가이드의 최신 권장사항:

| 이전 모델에서의 관행 | Opus 4.6에서의 변경 |
|---------------------|-------------------|
| "항상 도구를 써라" | "필요할 때만 써라" |
| "도구를 적극 활용해라" | "이해를 돕는 경우에만 도구를 써라" |
| "의심스러우면 도구를 써라" | 제거 (과도한 도구 사용 유발) |
| 명시적 CoT 지시 | Extended thinking 모드에서는 제거 |
| Prefill 응답 | 4.6부터 지원 중단, 명시적 지시로 대체 |

### 10-4. 과도한 엔지니어링 방지 프롬프트

```
과도하게 엔지니어링하지 마. 요청된 것만 변경해.
- 범위: 요청하지 않은 기능 추가, 리팩토링, "개선"은 하지 마
- 문서화: 변경하지 않은 코드에 주석이나 독스트링 추가하지 마
- 방어적 코딩: 발생할 수 없는 시나리오에 대한 에러 핸들링 추가하지 마
- 추상화: 한 번만 쓰이는 동작에 대한 헬퍼나 유틸리티를 만들지 마
```

## 13. 반복 개선(Iteration) 전략

프롬프트 엔지니어링의 진짜 핵심은 **첫 프롬프트가 아니라 반복 개선 과정**에 있다.

### 13-1. 실전 반복 개선 워크플로우

```
1. 초안 프롬프트 작성 (단순하게 시작)
2. 테스트 (3~5개의 다양한 입력으로)
3. 실패 패턴 분석
   - 어떤 입력에서 실패했는가?
   - 실패의 원인이 모호성인가, 맥락 부족인가, 과도한 제약인가?
4. 프롬프트 수정 (범용적으로, 특정 케이스에만 맞추지 않기)
5. 반복
6. 90%+ 성공률 달성 시 → 프롬프트 버전 고정 & 저장
```

### 13-2. 디버깅 체크리스트

| 문제 | 원인 추측 | 해결법 |
|------|-----------|--------|
| 답변이 주제를 벗어남 | 목표가 불명확 | 목표와 "왜" 필요한지를 명시 |
| 형식이 불일관 | 형식 미지정 | 예시 추가 또는 출력 형식 명시 |
| 작업이 너무 복잡 | 단일 프롬프트 과부하 | 프롬프트 체이닝으로 분할 |
| 불필요한 서두 | AI의 관성적 패턴 | "서두 없이 바로 답해줘" 추가 |
| 정보를 꾸며냄 | 할루시네이션 | "모르면 모른다고 해줘" 추가 |
| 변경 제안만 함 | 행동 vs 제안 모호성 | "변경해줘" (행동 동사 사용) |
| 답변이 너무 전형적 | Mode collapse | Verbalized Sampling 또는 다중 접근 요청 |

## 14. 컨텍스트 엔지니어링과의 연결

> [!quote] Anthropic 공식 블로그 (2025.09)
> "프롬프트 엔지니어링은 컨텍스트 엔지니어링의 필수적 빌딩 블록이다. 프롬프트 엔지니어링이 '올바른 단어를 찾는 것'이라면, 컨텍스트 엔지니어링은 '모델의 제한된 어텐션 예산에 어떤 정보 구성이 원하는 행동을 만들어낼 가능성이 가장 높은가?'라는 더 넓은 질문에 답하는 것이다."

**프롬프트 엔지니어링 → 컨텍스트 엔지니어링으로의 확장:**

| 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 |
|----|----|
| 하나의 프롬프트를 잘 쓰기 | 전체 정보 흐름을 설계하기 |
| 지시를 명확하게 | 어떤 정보가 언제 컨텍스트에 들어가는지 관리 |
| 원하는 출력 형식 지정 | 컴팩션, 노트테이킹, 서브에이전트로 장기 작업 관리 |
| 한 번의 대화에 집중 | 멀티 세션, 멀티 에이전트 워크플로우 설계 |

## 15. 요약: 프롬프트 엔지니어링 치트시트

```
🎯 목표를 명확히 → "왜" 필요한지 맥락 제공
📐 구조를 주기 → XML 태그로 역할/맥락/과제/형식 분리
📝 예시 보여주기 → 형용사 10개보다 예시 1개
🧠 생각하게 하기 → CoT, ToT, Self-Consistency
🎭 역할 부여 → 구체적 페르소나 설정
🔗 분할 정복 → 복잡한 작업은 체이닝
🎨 창의력 해방 → Verbalized Sampling, 제약 기반 창의성
🔄 메타 프롬프팅 → AI에게 프롬프트 설계를 위임
📊 자기 평가 → 9/10 미만이면 재시도
🔧 반복 개선 → 테스트, 분석, 수정, 버전 관리
```
