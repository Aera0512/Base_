# 핵심 요약 (예성 맞춤)
이 영상은 OpenClaw를 단순 설치 튜토리얼이 아니라,
**"메시징 게이트웨이 + 에이전트 런타임 + 메모리/스킬/보안"** 관점으로 설명한다.

핵심 포인트:
1. OpenClaw는 단순 챗봇이 아니라 **지속 실행 프로세스(gateway)** 기반 자동화 운영체계다.
2. Telegram/Discord 같은 채널 연동은 "입력 UI"일 뿐이고, 핵심은 **에이전트 실행/기억/도구 연결**이다.
3. 실전 퀄리티는 설치보다 **워크스페이스 구조, memory 관리, skills 품질 통제, 보안 정책**에서 갈린다.

# 실무적으로 바로 쓸 개념 6가지
## 1) Gateway 중심 사고
- OpenClaw는 long-running gateway가 이벤트를 받고 에이전트로 라우팅하는 구조.
- 즉, "한 번 질문하고 끝"이 아니라 **상시 운영 자동화**로 설계해야 함.

## 2) 채널은 인터페이스, 핵심은 오케스트레이션
- Telegram은 입력/알림 채널.
- 실제 가치: 세션/서브에이전트/크론으로 작업을 쪼개고 자동 실행.

## 3) Memory 설계가 성능을 결정
- 일일 로그(memory/YYYY-MM-DD.md) + 장기 메모리(MEMORY.md) 분리.
- 매 턴에 필요한 맥락만 불러오게 구조화해야 토큰 낭비/오답 감소.

## 4) Skill은 "설치"보다 "검증"
- suspicious 경고 스킬은 기본 보류.
- 실행형 스킬은 dependency, 외부 호출, API key 취급 먼저 점검.

## 5) 멀티에이전트는 역할 분담용
- 조사/코딩/리포트/정리 작업을 분리하면 메인 컨텍스트 오염이 줄어듦.

## 6) 보안은 기능보다 우선
- 외부 액션(메시지 전송, 계정 연동, 시스템 변경)은 항상 최소권한/승인 흐름.

# 예성 워크플로우로 번역한 실행안
## 오늘 바로 적용 (30~60분)
- [ ] Telegram 연동 상태 점검 (`channels status`)
- [ ] 핵심 스킬만 유지(저위험 중심), 의심 스킬 제거
- [ ] `HEARTBEAT.md`를 빈 상태로 유지해 불필요 폴링 차단
- [ ] OpenClaw 학습 자동화 프로젝트(YouTube→Obsidian) 단일 파이프라인부터 안정화

## 이번 주 적용
- [ ] n8n webhook → Python 요약기 → Obsidian 저장 자동화 고도화
- [ ] 실패 케이스 분기: 자막 없음/URL 오류/API 오류
- [ ] 템플릿 기반 노트(핵심개념/실습단계/주의점/리콜 질문) 고정

# 강의에서 얻은 운영 원칙 (짧게)
1. OpenClaw는 "AI 채팅 앱"이 아니라 "자동화 운영 런타임"으로 다뤄야 한다.
2. 좋은 결과는 모델보다 **구조(메모리/워크플로우/보안)** 에서 나온다.
3. 스킬은 많이 넣는 게 아니라, **신뢰 가능한 소수 정예**가 장기적으로 이득이다.
